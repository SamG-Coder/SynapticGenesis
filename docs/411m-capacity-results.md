# 411M live learning and generation on RTX 5080

The native C++/CUDA model successfully ran with **411,028,496 parameters and
65,536 spiking neurons** on the 16 GB RTX 5080. Learning, replay and scheduled
speech used the production live loop and shared model parameters. All eight
declared compatibility, allocation and capacity gates completed successfully
after the earlier width study exited. The [raw capacity result](../reports/capacity-411m.json)
and [verification record](../reports/shared-view-cuda-validation.json) retain
the protocol, source/binary identities, measured rounds and evidence hashes.

| Model | Channels | Spiking neurons per layer | Layers | Total spiking neurons | Learning byte targets/s | Generated bytes/s | Explicit live arrays after learning |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 104,851,472 parameters | 1,024 | 4,096 | 8 | 32,768 | 7,097.38 | 1,340.47 | 2.366 GiB |
| 411,028,496 parameters | 2,048 | 8,192 | 8 | 65,536 | 2,614.64 | 456.40 | 8.464 GiB |

The larger model has 3.92 times the parameters and twice the spiking neurons.
It is slower at this workload, but fits and executes finite updates on the same
GPU. The tokenizer uses UTF-8 bytes: these rates are byte tokens per second,
not directly comparable to another model's subword tokens per second. Neuron
counts describe this architecture's spiking state units, not biological neuron
equivalents. Both executions used driver 616.64, CUDA 13.3.73, TF32 and graph
generation, with ordinary desktop GPU contexts active.

## What was timed

The [declared protocol](411m-capacity-protocol.md) initializes each shape from
seed 1337. Both read the same admitted four-reader training fixture, use chunk
128 and uniform reservoir replay every four observations with 1,024 slots,
and generate 64 bytes every 128 observations. This short speed fixture is
separate from the larger prose curriculum and its 16,384-slot learning study.

After 128 warm-up observations, each shape performs three consecutive rounds
of 512 source observations. Measured source targets are 65,499, 65,444 and
65,536 bytes. Each round also has 16,384 replay targets and 256 generated
bytes. All exposure counts match between sizes. Live timing includes source
learning, replay, scheduled speech, synchronization and small speech writes;
initialization and warm-up are excluded. No benchmark checkpoint is saved.

At 105M the three learning rounds took 9.229, 9.249 and 9.224 seconds. At 411M
they took 25.051, 25.031 and 25.063 seconds. The table reports the median of
each round's source-target throughput. Training losses remain finite; their
values are not held-out language-quality measurements.

Generation uses the same live speaker after learning. Following one untimed
1,024-byte generation, three timed repetitions restore identical recurrent
state and sampling RNG at fixed weights. Prompt processing and CPU sampling
are included. Generated bytes match exactly across repetitions. The 411M
repetitions took 2.249, 2.228 and 2.244 seconds. The table reports the median
generated-byte throughput.

## Memory and compatibility

The borrowing constructor avoids creating a second set of weights, gradients,
Adam moments and decay masks for each execution view. Five FP32 arrays at
411M occupy 8,220,569,920 bytes, or 7.656 GiB. Twelve small native allocation
controls verify that the constructor removes exactly `20 * parameters` bytes
from the explicit float-allocation peak while preserving retained allocations.
The old 411M construction path was not deliberately run to exhaustion.

The separate allocation-only test creates the root and speaker, then exercises
both four-shape caches through creation and eviction. Its measured explicit
float-buffer peaks were 2,738,903,280 bytes (2.551 GiB) at 105M and
9,476,925,680 bytes (8.826 GiB) at 411M. All observed float allocations were
released. These commands perform no forward pass or learning.

During the actual speed workload, the 411M live engine retained 9,087,870,900
bytes (8.464 GiB) of counted model arrays. The minimum round-boundary free
VRAM snapshot was 6,093,275,136 bytes (5.675 GiB). This is not a guarantee of
that much spare memory at every instant. The allocation ledger counts float
buffers; live-array counts also include integer token buffers. Both exclude
CUDA/cuBLAS internals and graph overhead. Neither method measures a continuous whole-process peak.
Longer prompts, larger batches and optional consolidation require separate
memory checks.

The completed checks before the speed panel were:

- 12 allocation comparisons; 48 exact forward/backward/optimizer/state and
  owner-lifetime cases; 26 owner/shape guards; six bounded scorer caches with
  54 accesses, including eviction and unchanged owner state.
- All 18 existing CTest checks.
- 48 live commands across all six cell types and FP32/TF32: exact old/new
  checkpoint and speech bytes, plus exact resumed checkpoints.
- 240 training-prefix, context, language-scoring, decoding and cue-memory
  commands, yielding 204 exact comparisons. Only declared timing fields are
  excluded from comparisons.
- The two allocation-only shapes above and four tiny capacity-observer calls
  reproducing complete production checkpoints in FP32 and TF32.

The verification record authenticates 336 evidence files and all 312 artifacts
named by the caller-compatibility result. The main executable used by earlier
studies remains byte-identical. The new constructor changes allocation and
ownership, not neuron equations, checkpoint format or the shared forward path.

## Actual output and limits

These are the last scheduled completions after 1,664 source observations,
selected by position rather than quality. The prompt was `The bird ` and each
completion contains exactly 64 generated bytes. Raw speech hashes and byte
hex are retained in the verification record.

105M completion:

```text
os. He thill your doing the corgest ust monge it, soust lowle
wo
```

411M completion:

```text
idp. The clowerss lomed the noog the
courdled hind hare you mugh
```

Both remain weak language output. This experiment establishes memory
feasibility and short live learning/generation speed at 411M. It does not
establish useful question answering, long-term retention, quality improvement
over 105M, or performance after training on the full selected corpus. The
random benchmark founders are discarded and are not parents or teachers.
Full curriculum training with separate evaluation is the next learning step;
increasing size alone is not a quality result.
