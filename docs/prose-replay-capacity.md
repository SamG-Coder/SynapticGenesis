# Larger ordinary replay reservoir

The [coverage reconstruction](prose-replay-coverage.md) found that final-stage
rehearsal repeatedly selected 755 distinct earlier-source windows, covering
approximately 0.85% of the earlier target-byte positions. This experiment tests
whether a larger ordinary replay reservoir improves retained reading and held-out
prediction. It adds no learned selection/scoring pass to the native loop.

The [specification](../data/prose-replay-capacity-v1.json) fixes two fresh
founders, one 2M and one 105M, with **16,384 replay slots**. Each is compared with
its completed 1,024-slot control from the original size study. Both use seed
1337, the original learning rate 0.0003, one replay update per four source
observations, and the complete 216,289-observation curriculum. The selected
55-book source edition, byte vocabulary, architecture and native executable
stay fixed. New founders import no learned weights or teacher output.

The comparison is exploratory: the larger capacity was chosen after seeing
baseline coverage and regression. It uses one seed, and greater text coverage
does not automatically establish better language learning.

| Setting | Completed control | Fresh candidate |
| --- | ---: | ---: |
| Replay slots | 1,024 | 16,384 |
| Source observations | 216,289 | 216,289 |
| Source target pairs | 27,680,129 | 27,680,129 |
| Scheduled replay updates | 54,072 | 54,072 |
| Generated bytes during learning | 41,472 | 41,472 |
| Learning rate | 0.0003 | 0.0003 |
| Source chunk | 128 bytes | 128 bytes |

The actual replay target bytes and per-stage distribution must be reported.
Increasing the capacity changes admission/shrinkage RNG consumption and the
selected examples. Equal seed and cadence do not make those targets identical
to the smaller reservoir. The two new candidate sizes must, however, have
identical replay-policy payloads at each corresponding endpoint.

At stages one, two, three and four, assess the same four validation books,
the same two early-reader training monitors, and the same four raw prompts.
Preserve every book result and generated byte sequence. Report per-book
differences and the equal-book validation mean against the matching 1,024-slot
control. No reserved tests are scored and no model is automatically promoted.

Each candidate's untouched `initial.ckpt` must match its control in initial
parameters, Adam moments, recurrent state and hyperparameters. The comparison
streams these arrays through a hash rather than loading the entire large
checkpoint into Python. All initial metadata must match except the payload
checksum, and the replay policy may differ only in capacity. This check occurs
after the fresh native learning invocation has closed its output files and
before its assessment results enter the comparison.

## Runtime and implementation

The driver waits on the learning-rate study's verified Windows process handle.
It then requires successful completed reports for the original three-size
comparison, matched neuron panel and learning-rate continuation, including the
exact resumed-control checkpoint gate. The lower-rate result is neither a source
of candidate weights nor a rule for choosing this experiment's learning rate.
This keeps the rate and capacity questions separate.

The new founders run sequentially and use the existing native `live` command.
There are two new native learning invocations and 80 read-only assessment
invocations. The shared founder helper now accepts an explicit replay capacity
with the historical value of 1,024 as its default. Its argument builder is
reused by both the normal CLI and this experiment. Checkpoint assessment stays
in the previously extracted shared module.

The diagnostic counter reader now uses the common bounded policy reader. Its
former 16,384-word limit was too small for the larger descriptor record even
though the native loader supports it. At four groups, a full 16,384-slot pool
uses 49,189 words, or 393,512 host policy/checkpoint bytes. Relative to the old
pool this adds 360 KiB. Source-library, CUDA-array and other process costs are
separate and still need measurement.

Native session time includes replay, scheduled speech and checkpoint saves.
These fresh founders save every 2,048 observations; the original 105M
continuation saved every 8,192. Full-run times therefore do not provide a
controlled size-speed comparison. The experiment adds no neural replay-scoring
pass, but descriptor management and serialization still have a cost.

## Verification boundary

The [CPU preflight](../reports/prose-replay-capacity-preflight.json) passed:

- Both default argument lists exactly match the archived original native
  founder commands. At capacity 16,384, only that argument changes.
- All eight completed 2M/105M endpoint counter records remain unchanged through
  the revised bounded reader.
- The complete assessment wrapper authenticated both final control checkpoints
  and replayed their 20 archived native outputs, preserving every book and raw
  sample result. These were CPU journal replays, not new CUDA calls.
- The initial-state guard accepts identical saved arrays and rejects an
  altered weight byte or an unexpected capacity.
- A deliberately synthetic 49,189-word record exercises the larger diagnostic
  read bound. It is not a valid trained model and is never passed to CUDA.
- Invalid capacities, changed replay-update budgets and an incomplete
  predecessor are rejected. The latter fails before a learning call.

The preflight made no CUDA calls. Fresh larger-reservoir training, agreement of
the real initial arrays, and any quality benefit remain pending. Development
uses a separate checkout so the already running studies retain their declared
code and source identities. The protocol pins that checkout's exact code and
the original native executable; none of those files may change during the run.
